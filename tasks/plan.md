# 产品图片工作台优化实施计划

## 2026-07-14：分图片类型推荐提示词

### 目标

- 主图、A+ 图片、场景图、细节图、尺寸图、卖点图、宣传图、对比图各内置 3 个推荐提示词。
- 推荐词填入后保持可编辑；用户可保存为当前图片类型的个人模板，并可继续修改更新。
- 已保存模板严格按图片类型隔离；旧版全局模板迁移后保留并归入主图。

### 实施与验收

1. 依据 Amazon 官方图片/A+ 创意规范和 OpenAI 官方提示词指南整理结构化推荐词，禁止编造尺寸、参数、认证、优惠和对比结论。
2. IndexedDB 升级到 v3，为提示词模板增加 `imageType` 索引和旧数据迁移。
3. 推荐词使用紧凑下拉框展示，避免占满生成参数栏；选择后可编辑、另存和更新。
4. 测试覆盖 8 类 × 3 个推荐词、类型隔离、编辑更新和旧模板迁移；完成前端 lint、type-check、test、build 与浏览器验收。

## 2026-07-13：GPT Image 2 官方质量与比例转换

### 目标

- 模型配置和生成参数中的质量严格使用 OpenAI 官方顺序 `auto/low/medium/high`，界面显示为“自动、低质量、中等质量、高质量”。
- 图片比例严格使用 `自动、1:1、1.62:1、2:3、3:2、3:4、4:3、4:5、5:4、9:16、16:9、21:9` 的固定顺序。
- 生成和参考图编辑时，由后端 Provider Adapter 把比例转换为满足 `gpt-image-2` 约束的像素尺寸；质量保持独立并原样发送。

### 接口与兼容性

- 平台 API URL、Method、请求/响应字段不变；继续使用 `supportedSizes`、`supportedQualities` 与任务 `parameters.size/quality`。
- 现有明确像素尺寸继续透传，避免旧模型配置立即失效；比例转换只作用于 `gpt-image-2` 及其带日期快照名称。
- OpenAI 与 OpenAI-Compatible 使用同一模型能力语义，不根据某个中转站的自定义质量档位生成预设。

### 验收标准

- 模型编辑页按指定顺序显示“图片比例”和“生成质量”，不出现 `1K/2K/4K`、`standard` 或 `hd` 预设。
- 生成页使用相同名称与后台配置顺序，并继续遵循“自动优先、用户选择优先”的现有行为。
- JSON 生成和 multipart 参考图编辑请求都发送转换后的像素值；API 调用审计记录实际出站尺寸。
- 前后端测试覆盖全部 12 个比例值、官方质量顺序、非法极端比例拒绝以及旧像素值兼容。

## 2026-07-13：模型参数语义与后台编辑交互优化

### 目标

- OpenAI 类模型将“图片比例”和“生成质量”分开，质量只展示 `auto/low/medium/high` 等该协议实际使用的值。
- Gemini 类模型将“画面比例”和“输出分辨率”分开，`1K/2K/4K` 只作为分辨率，不再与比例组合成十余个重复尺寸项。
- 中转站、模型、用户、角色、权限和产品等长表单从列表旁的内嵌编辑改为独立右侧抽屉，抽屉内容单独滚动，列表和上下文保持原位。

### 实施切片

1. 参数预设按 Provider 类型分组，并为现有自定义值保留兼容显示。
2. Gemini Provider Adapter 将画面比例与分辨率映射到 `generationConfig.imageConfig`；OpenAI `gpt-image-2` 将平台比例映射为官方像素尺寸。
3. 新增可复用、具备焦点约束的编辑抽屉，并迁移中转站/模型、用户/角色/权限和产品管理长表单；单字段短编辑继续保留行内方式。
4. 补充组件、参数校验和 Provider 请求测试，完成前后端全量验证与浏览器验收。

### 接口与兼容性

- 平台 API URL、Method、请求/响应字段不变；继续使用 `supportedSizes` 和 `supportedQualities`。
- `supportedSizes` 增加严格白名单内的画面比例值，既有像素尺寸继续兼容；本地运行模型数据按精确模型 ID 更新。
- Gemini 请求发送大写 `1K/2K/4K`；数据库与任务参数继续使用小写规范值，避免破坏既有比较逻辑。
- OpenAI-Compatible `gpt-image-2` 与官方 OpenAI 使用同一比例到像素转换，不套用中转站自定义预设或 Gemini 映射。

### 验收标准

- 编辑 OpenAI-Compatible `gpt-image-2` 时，不再同时出现 `1K/2K/4K` 和低/中/高两套质量选项，也不再显示 1K/2K/4K 与比例的笛卡尔积。
- 编辑 Gemini 模型时，比例和输出分辨率各选择一次；请求中分别出现 `aspectRatio` 与 `imageSize`。
- 打开新增或编辑后，管理列表不改变列宽、不被表单向下撑长；产品、用户、角色和模型等长表单抽屉可独立滚动、Esc 关闭并恢复焦点。
- 现有模型中的自定义尺寸或质量值不会因打开编辑器而丢失。

## 目标

把当前单任务、三栏堆叠的“项目工作台”调整为以产品为中心的多任务工作台：用户提交一项生图任务后可立即切换图片类型或产品继续创建任务，所有任务通过同一条 SSE 实时更新，并在完成或失败时给出明确提醒。

## 前置假设与设计决策

- “同时生成”首先指前端不阻塞后续提交；任务可并存于后端队列，真正并发数继续由 Worker 与 Provider 并发配置决定。
- 用户界面统一使用“产品”；后端 `Project` 类型、URL、表名和权限键保持不变，避免不必要的接口迁移。
- 完成提醒使用应用内提醒卡片和任务中心，不请求浏览器系统通知权限。
- 不新增 API、不使用轮询；通过现有 `/api/v1/events/tasks` 全局 SSE 连接分发任务事件。
- 产品素材和生成记录改为按需打开的次级空间，默认工作区只保留生成参数与当前类型结果。

## 当前态、允许中间态与目标态

| 能力 | 当前态 | 允许中间态 | 目标态 |
| --- | --- | --- | --- |
| 任务状态 | 单个任务、每任务一条 SSE、运行时禁用表单 | 多任务状态已建立，旧结果面板仍显示选中任务 | 单条全局 SSE、多任务中心、按任务取消/重试/查看 |
| 任务提交 | 有活动任务时拒绝新提交 | 同一产品内可连续提交 | 跨产品/图片类型均可连续提交，创建请求期间仅防重复点击 |
| 图片类型 | 标签可切换但运行时禁用，结果和提示词不隔离 | 标签始终可切换，结果按类型隔离 | 每个产品/类型保留独立提示词草稿与结果上下文 |
| 项目概念 | 界面大量使用“项目” | 核心工作台改称“产品” | 所有面向普通用户的业务文案统一为“产品” |
| 页面密度 | 参数、结果、素材/历史同时展示 | 次级内容入口已收拢 | 默认双栏，素材、记录、任务中心按需打开 |

## 实施切片

### 分片 1：多任务状态与实时事件

**验收标准**

- 第一项任务处于 `QUEUED` / `RUNNING` 时仍可提交第二项任务。
- 一条无任务过滤参数的 SSE 连接可以更新当前会话内的所有任务。
- 产品或图片类型切换后，原任务仍在任务中心持续更新。
- 取消、重试操作作用于明确的任务 ID；创建请求尚未返回时仍防止重复提交。
- 完成、失败、取消、超时事件只产生一次应用内提醒。

### 分片 2：产品和图片类型工作区

**验收标准**

- 顶部使用可见、可键盘操作的“当前产品”选择器，并提供产品设置和新建产品入口。
- 图片类型标签在任务运行期间保持可用，并增加“宣传图”。
- 结果画布只显示当前产品 + 当前图片类型下选中的任务结果。
- 提示词按“产品 ID + 图片类型”保存草稿，来回切换不丢失。

### 分片 3：任务中心、提醒和页面减负

**验收标准**

- 顶部可查看活动任务数，任务中心列出产品、图片类型、状态和操作。
- 任务完成或失败时显示提醒；点击“查看结果”切换到对应产品和图片类型。
- 主工作区由三栏改成参数 + 结果双栏。
- 产品素材和生成记录不再默认占据第三栏，改为按需打开的辅助面板。

### 分片 4：文案、可访问性和交付验证

**验收标准**

- 普通用户可见的业务文案统一使用“产品”，技术管理界面的 `Project` 标识不暴露给用户。
- 任务中心、提醒、产品选择和辅助面板具备明确的可访问名称、焦点和关闭行为。
- 320、768、1024、1440px 无横向溢出，浏览器控制台无新增错误。

## 必须保持的行为

- 登录、退出、CSRF、RBAC、租户隔离和对象权限检查不变。
- 前端只调用 Go 后端；AI 密钥不进入浏览器存储、日志或客户端配置。
- 任务状态仍只由 SSE 推进，不新增 `setInterval`、重复 fetch 或轮询。
- 任务创建参数、模型能力、图片上传校验、资产下载和历史详情保持兼容。
- 不覆盖工作区中与本任务无关的现有改动。

## 允许的中间态

- 多任务 hook 落地后，结果区可暂时只展示当前上下文最新任务。
- 产品文案可按组件逐步替换，但每个切片完成时相关测试必须恢复通过。
- 任务提醒先覆盖当前会话中新建任务；刷新后的历史结果仍由生成记录承接。

## 禁止的半迁移状态

- 不能仅移除按钮禁用，却继续由 hook 拒绝第二项任务。
- 不能为每个任务长期创建独立 EventSource，或用轮询补偿事件丢失。
- 不能切换图片类型后仍展示另一类型的结果或提交错误的 `imageType`。
- 不能以 UI 重命名为由修改后端 `Project` API、数据库或权限键。
- 不能直接显示 Provider 原始错误、Authorization、API Key 或图片 base64。

## 失败模式与边界场景

- 两次快速点击发生在同一创建请求未返回时。
- 两项任务乱序完成、某项只产生部分图片后失败、重复终态事件。
- 切换产品后旧产品任务完成；提醒点击后需要正确回到原产品/类型。
- 当前类型没有结果、产品被归档、模型列表失效、SSE 临时断开。
- 超长产品名、窄屏、多项任务并存、任务取消或重试接口失败。

## 回归测试映射

- `taskWorkbench.test.tsx`：连续创建任务、单 SSE 路由、完成提醒、产品/类型切换、参数契约。
- `authFlow.test.tsx`：无产品引导、登录/退出和权限入口。
- `projectAssetsWorkbench.test.tsx`：产品素材、上传、引用、筛选和操作入口。
- `modalAccessibility.test.tsx`：任务中心/辅助面板复用弹窗的键盘行为。
- 全量：`npm run lint`、`npm run type-check`、`npm test -- --run`、`npm run build`。

## 修改边界

允许修改 `frontend/src/**`、对应测试及 `tasks/**`。本轮不修改 `backend/**`、`deploy/**`、数据库迁移和 API/SSE 合同。

# 参考图、尺寸和并发任务异常修复计划

## 已确认根因

- 生成任务携带参考图时，Worker 已读取图片，但仍把操作标记为 `generate`，导致兼容适配器调用 `/images/generations` 并丢弃参考图字节。
- Euzhi 要求参考图调用 `/images/edits`，且 multipart 图片字段使用 `image[]`；当前单参考图使用了 `image`。
- 当前本地 `gpt-image-2` 模型能力配置只有 `1024x1024`、`standard`、单张输出，与 Euzhi 文档中的 `medium` 示例和项目已有 GPT Image 2 模板不一致。
- 最近两项并发任务失败不是队列丢失，而是 Provider 返回余额不足；成功任务之后剩余额度低于下一张所需额度。

## 修复切片与验收标准

### 分片 A：参考图请求路由

- 携带任意输入图片的生成任务必须转换成 Provider `edit` 操作。
- OpenAI-Compatible 编辑请求必须调用 `/images/edits` 并以 `image[]` 上传所有参考图。
- API 调用审计只能记录参考图数量和 endpoint，不能记录图片内容、Key 或 Authorization。

### 分片 B：参数与错误反馈

- 增加适用于 OpenAI-Compatible `gpt-image-2` 的正确能力模板。
- 本地已部署模型修正为文档支持的尺寸、质量和格式；不修改 Provider Key。
- Provider 余额不足应归一化为稳定错误码，并在前端显示简体中文可操作提示。

### 分片 C：验证

- 回归测试证明旧实现会把参考图发送到错误 endpoint，修复后通过。
- 前后端全量测试、Lint、类型检查和构建通过。
- Docker 重建后，审计日志显示参考图任务的 `operation=edit`、`endpointPath=/images/edits`、`referenceImageCount>0`。
- 真实计费生图仅在余额足够时执行；余额不足时停止重复调用，避免无意义扣费或失败任务。

## 接口影响

- 平台任务创建接口 URL、Method、请求体和响应体保持不变。
- `IMAGE_GENERATION + referenceAssetIds` 仍是业务层“参考图生成”，只在 Worker 到 Provider 的内部适配层映射为图片编辑 endpoint。
- 新增内部错误码 `PROVIDER_INSUFFICIENT_QUOTA`；现有 SSE 结构不变。
